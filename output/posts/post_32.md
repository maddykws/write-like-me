The Python code review comment I write most as a manager isn't about bugs. It's "would the on-call engineer understand this at 3am?"

Clever code is a tax your team pays later, usually during an incident, usually at the worst time.

What I coach for:
- Boring, obvious code over impressive one-liners
- Names that explain intent, not just type
- Comments for the 'why', when the 'what' isn't enough

I'd rather maintain readable code that's slightly slower than brilliant code no one can touch. The team's velocity lives in readability.
